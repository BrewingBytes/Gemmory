## Problem Statement

Gemmory exists only on Google Play: v1.0.0 (22) is on the closed test, with no production access and no production data yet. The founder wants the same game on iPhone: "we need to make it ios too". The goal is full feature parity with Android in the App Store, so that every later feature lands on both stores.

The project was set up for this. Round 1 decision R3-14 chose Kotlin Multiplatform with a pure-Kotlin `commonMain`, and Compose Multiplatform "later" for the iOS UI. But today only the logic is shared:

- `:shared` (7.4k lines) holds the converter, game, policy, save, remote and timelapse logic. It targets `android` and `jvm()` only and has never been compiled for iOS.
- `:androidApp` (23.7k lines, 110 files) holds every screen and every platform service. 71 of its files import `android.*`, and there are 789 string-resource references.

## Demand Evidence

None yet, and the founder said so: "No one asked yet." This is a strategic bet. The reasons are that iPhone players spend more, iOS is half the market, and the KMP setup always assumed it. No iPhone user has asked to play, and nobody has watched a tester play Android unprompted ("Haven't watched anyone").

The design therefore names a proof metric for each stage and a pause condition (Success Criteria) instead of assuming demand.

## Status Quo

iPhone users who like diamond painting play the stock-library apps (Diamond Painting ASMR, Diamond Painting · Art by Number, Diamond Paint) or convert photos with Dotterly or DiamondCrafts. None of these has Gemmory's share loop built around the time-lapse.

A Gemmory time-lapse shared to an iPhone user today leads to a Play Store link they can't use. So far that's an assumption about leakage, not something measured.

## Target User & Narrowest Wedge

- **Target user:** the same adult diamond-painting player as on Android, on an iPhone. No specific person has been named yet; the Assignment fixes that.
- **Narrowest wedge:** offered as "core loop + ads + VIP as the first App Store release", and declined by the founder in favour of staged parity. The stages below still give a TestFlight build that the core loop runs on early.

## Constraints

- Every rule in AGENTS.md carries over unchanged:
  - Adults only: not the Kids category, and no child-directed ad settings.
  - User photos never leave the phone. No upload, and photos are excluded from iCloud backup and device-to-device transfer.
  - No ads on the play canvas. Interstitials are shown only after the player leaves the completion screen, within the caps.
  - A wrong-color tap is rejected with no state change, and the save log is an ordered list of placed cell indices.
  - `shared/src/commonMain` stays pure Kotlin.
  - UI follows `docs/design-system.md`.
  - Every PR shows screenshots. On iOS that means simulator screenshots.
  - Every long-running command has a hard `timeout`.
- Android production comes first. iOS work never blocks the Android production launch, #74 T34 or the founder's owed Android items, and Android wins any week where the two conflict.
- Android must not regress while its UI moves into the shared module.
- Solo founder. Machine: Xcode 26.6, no iOS simulator runtimes installed yet.
- All 11 languages are required on iOS.

## Premises

1. iOS is a strategic bet, not demand from players. Each stage has a proof metric and a pause condition.
2. Android production keeps priority.
3. **(Revised by the founder)** TestFlight only until full parity, then the first App Store release. The stages are build milestones, and TestFlight cohorts give the early read.
4. **(Revised after the second opinion, verified in code)** The UI is Compose Multiplatform, so R3-14 holds. The play canvas and the frame layers are currently `android.graphics` drawn on `nativeCanvas`:
   - `play/CanvasRenderer.kt`, `ui/GemRenderer.kt` and `timelapse/FrameArt.kt`.
   - The call site is `PlayScreen.kt:625`, `drawIntoCanvas { renderer.draw(it.nativeCanvas, …) }`.

   Those three are rewritten to common Compose `DrawScope` code, and Android uses the rewritten code too. They must meet the **renderer golden bar** (defined under Success Criteria) against today's output. `GlFrameWriter.kt`, the EGL bridge onto the MediaCodec surface, stays Android's encode service and is not rewritten. Platform services sit behind Kotlin interfaces. Strings decision E1 is reopened.
5. All AGENTS.md rules carry over, and Android must not regress.
6. Distribution (Apple account, App Store Connect, TestFlight, iOS AdMob and Firebase apps, privacy manifest and labels, macOS CI) is part of the design.

## Approaches Considered

### Approach A: Fork-and-port (iOS-only Compose Multiplatform app)

Copy the screens into a separate iOS app and leave Android untouched. Rejected: every later feature and fix ships twice, the two UIs drift apart, and parity breaks after launch.

### Approach B: One shared UI module, staged (CHOSEN)

See Recommended Approach.

### Approach C: Native SwiftUI over a `:shared` XCFramework

Rejected: about 20k lines of UI rewritten in Swift and maintained forever, three renderers to keep in step, and it goes against R3-14, which held up when tested in this session.

## Recommended Approach

**Approach B: one shared Compose Multiplatform UI.** The founder picked it (D5).

Module layout (the eng review confirms it):

- **`:shared`** stays pure-Kotlin logic. It gains the targets `iosArm64` and `iosSimulatorArm64`. Does `iosX64` matter? Only Apple-silicon Macs are in use, so probably not; eng confirms.
- **`:composeApp`** (new, Compose Multiplatform) holds:
  - every screen (Gallery, Play, Completion, Photo flow, Paywall, Settings, Streak, sheets);
  - the design-system components and tokens;
  - the rewritten renderers: the gem/canvas renderer and the time-lapse frame art in common `DrawScope`/Skia code.

  Platform services are interfaces in `:composeApp` (or a small `:platform` API module), implemented per shell:

  | Service | Android today | iOS |
  |---|---|---|
  | Ads + consent | AdMob, UMP, Unity mediation, GPP | Google Mobile Ads iOS SDK, UMP, ATT prompt, Unity adapter |
  | VIP + remove_ads | Play Billing (VIP subscriptions, `remove_ads`) | StoreKit 2 (VIP subscription, `remove_ads` non-consumable, restore). Entitlements are per store, with no cross-platform carry-over (no backend). The Paywall and the restore help text say so in all 11 languages. |
  | Video encode + compositing | MediaCodec + GL compositing in `GlFrameWriter` | Core Image/Metal compositor into `CVPixelBuffer` + AVAssetWriter |
  | Face detection (photo crop) | ML Kit | Vision (`VNDetectFaceRectanglesRequest`) |
  | Analytics / crash | Crashlytics always on (D17); Firebase Analytics under UMP consent (Consent Mode v2, R3-7) | Firebase iOS SDK from Stage 2, split the same way: Crashlytics always on, declared in the privacy manifest and nutrition labels; Analytics under UMP consent |
  | Review prompt | Play Review | `AppStore.requestReview` |
  | Photo pick | Android photo picker | PHPicker (no library permission) |
  | Share | Android share sheet | `UIActivityViewController` |
  | Reminders | Android notifications | `UNUserNotificationCenter` |
  | Widget | Glance | WidgetKit (Swift; cannot be Compose) |
  | Achievements | Play Games v2 (`GamesBackend`) | Game Center (`GamesBackend` implementation, CEO C2) |
  | Install attribution | Install Referrer (T55/T56 channel links, T50 fresh-install picture) | App Store Connect campaign links (CEO C7); no fresh-install picture handoff (CEO C6) |

- **`iosApp/`** (new Xcode project): the Swift entry point, the iOS service implementations, the widget extension, and the SPM packages (GoogleMobileAds, UMP, Firebase).

**Time-lapse compositing (R1-4).**

- The per-frame plan lives in `commonMain` as pure Kotlin: which layers are shown, and each layer's alpha at each timestamp (photo intro, dim, fades, end-card band).
- The layers come from the common `FrameArt`.
- Each platform composites and encodes them: Android keeps its GL path in `GlFrameWriter` (#117 frame-loss work unchanged), and iOS uses Core Image or Metal into `CVPixelBuffer`.
- Composited frames at fixed timestamps from both platforms are checked against the same goldens, under the cross-platform bar of the renderer golden bar.
- Moving all compositing into common code was rejected, because it would re-open Android encode cost (#117).

## Success Criteria

**Renderer golden bar (one definition, used everywhere this doc says "golden"):**

- **Harness:**
  - A connected androidTest on one pinned emulator image (the API level and image are pinned in the eng review and written in `docs/agents/workflow.md`).
  - Each renderer draws into an offscreen software bitmap, never the GPU surface, so the output is deterministic.
  - Today's renderers draw through `android.graphics.Canvas`. The rewritten ones draw through `CanvasDrawScope` into an `ImageBitmap` on the same image.
- **Fixed inputs:**
  - One bundled picture per crop ratio (1:1, 3:4, 4:3) at the largest canvas size.
  - Fixed save logs for the empty, half and full states, at each zoom bucket and each highlight style.
  - `GemRenderer` tiles for every gem color.
  - `FrameArt` layers and composited frames at fixed timestamps: intro, mid and end card.
- **iOS side (Stage 2):**
  - An XCTest in `iosApp` runs on one pinned iOS simulator runtime in the macOS CI job.
  - It drives the shared frame plan through the iOS Core Image/Metal compositor and compares the composited frames at the same fixed timestamps: intro, mid, end card.
  - The common renderers' own output on iOS is checked by a `:composeApp` `iosSimulatorArm64Test`.
- **Storage:** one shared directory, `goldens/renderer/` at the repo root. It is packaged into the Android device-test assets and into the XCTest bundle, so both platforms read the same files.
- **Pass, per layer** (starting values; the eng review fixes them from the Stage 0 measurement):
  - **Geometry** (canvas cells, gem tiles, highlights): ≤ 0.5% of pixels differ by more than 8/255 in any channel, and no pixel differs by more than 32/255. These are compared with text regions masked out.
  - **Text regions and the blur band:** SSIM ≥ 0.98 per region. Text moves from `StaticLayout` to `TextMeasurer`, and the blur from `BlurMaskFilter` to a common blur.
  - **Cross-platform** (iOS output against the Android goldens): SSIM ≥ 0.97 per composited frame, because glyph rasterization and the compositor differ between platforms.
- **Scope:** Android checks (Stage 0 subset, 1a full set) use the geometry and text/blur bars. iOS checks (Stage 2) use the cross-platform bar.

**Per-stage gates.** Each has a metric and an action when it's missed. TestFlight cohorts are small, so they are signals, not significance.

### R3-1 — feasibility (blocking)

**Problem**

### CEO review sections (strategy depth)

- **1. Architecture.** The dependency graph is `:shared` → `:composeApp` (screens, design system, DrawScope renderers, service interfaces moved from `androidApp`) → the `:androidApp` and `iosApp` shells. The WidgetKit extension reads streak state through an App Group.
  - OK: the coupling is justified, because the interfaces already exist.
  - WARNING: `:composeApp` is a shared point of failure, held by the per-PR Stage 1 gates.
  - WARNING: the bridging pattern for Swift-only APIs (StoreKit 2, `requestReview`, WidgetKit) goes to eng (R3-11).
- **2. Error & rescue (capabilities).** Two gaps, both owned by eng:
  - (a) The app is backgrounded mid-encode. iOS suspends it within about 30 s, unlike Android. It needs `beginBackgroundTask` or resume-on-foreground, with the user seeing Android's encode states, never a silent stall.
  - (b) Low disk when saving a converted photo. It must show Android's save-fail copy.

  Also stated for eng: StoreKit 2 `Transaction.updates` with revocation on refund; ATT denied → non-personalized ads; UMP failure → no ad request (mirrors Android); `RemoteSource` and `GamesBackend` keep their existing contracts.
- **3. Security.** No new endpoints and no backend.
  - Medium: photo exclusion during iPhone-to-iPhone migration is unverified (open question 7, eng, before Stage 2).
  - Low: CI secrets (App Store Connect API key, signing certificate and profile) get a rotation note.
  - Low: the privacy manifests of the GMA, Unity and Firebase SDKs must aggregate (Stage 3 gate).
- **4. Edge cases.**
  - Interrupted placement: handled by the shared save log.
  - No system back button on iOS: every screen needs a back affordance or edge swipe (design review).
  - Rotation and iPad: open question 3, eng.
  - VIP Family Sharing: pending, default off (eng, founder confirms).
- **5. Code quality.** The plan fits the existing seams. `RenderAssets` is interim and is deleted in 1b.
- **6. Tests.** Gap: an iOS mirror of `BackupRulesTest`, asserting that every photo-derived file carries the backup exclusion. The rest are already in the plan: golden bar, connected suite, XCTest frames, StoreKit configuration tests.
- **7. Performance.** The Stage 0 gate covers frame time. iOS encode time and memory at the largest canvas are measured in Stage 2 (open question 10).
- **8. Observability.** iOS Crashlytics and Analytics from Stage 2. `docs/reading-first-30-days.md` needs a platform split per metric.
- **9. Deploy.** iOS reaches players only at Stage 5, with TestFlight before that. The Android 1a release ships at 100% (R9-1), with a hotfix as rollback. Release tags: `v*` stays Android, and the iOS tag is decided in eng.
- **10. Trajectory.** Reversibility 2/5: Stage 1 moves Android onto Compose Multiplatform, a one-way door in practice. Debt: interim `RenderAssets`, two compositors (GL and Core Image) kept in step by goldens, and iOS-only code in Swift. A new engineer in 12 months finds one UI module and two thin shells.

Design and UX.** There is UI scope: iOS back navigation, safe areas and Dynamic Island, the ATT pre-prompt and its timing (R3-13), the Game Center sign-in moment, restore and per-store copy, and iOS haptics against the design system's haptics rules. **Run `/plan-design-review` (Phase 5) before implementation.**
