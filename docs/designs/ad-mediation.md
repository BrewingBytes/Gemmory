## Status Quo
Every ad impression in the closed test is a Google test ad worth €0. Content is 50 bundled pictures. The remote-picture pipeline (#43) is built, but `tools/remote/PROVENANCE.md` has zero rows, so nothing has been published through it.

## Target User & Narrowest Wedge
The daily closed-test player who already opens the app every day. The narrowest wedge that makes money is no new feature: the existing rewarded unlocks and post-completion interstitials, served by real demand.

## Constraints
- Ad rules are unchanged (AGENTS.md, design doc Ad rules): no ads on the canvas, interstitials only after leaving the completion screen under the caps, rewarded opt-in, no banners. `shared/policy/AdPolicy` and `RewardedRules` stay the single source of truth.
- Adults only (18+), not child-directed.
- User photos never leave the phone; the ad SDKs never see them.
- Every new SDK triggers the Data safety re-check (`docs/play-compliance.md` → "Re-check this section when").
- No secrets in the repo. Ad IDs are not secret and live in committed build config, not hardcoded constants.

## Premises (founder agreed 1-6 on 2026-10-18; refined 5 and 7 confirmed at doc approval the same day)
1. Real ads come first: a production AdMob app and ad units, IDs from build config (not hardcoded), Google test IDs kept for debug builds.
2. "Higher-paying ad" means AdMob mediation **bidding** with Google's Unity Ads adapter. No custom code racing two SDKs; Gemmory's ad rules stay exactly as they are.
3. app-ads.txt on a real root domain (e.g. a GitHub Pages site `brewingbytes.github.io`, set as the Play developer website) is a launch blocker, not polish.
4. Unity needs consent wiring (custom ad partner in AdMob → Privacy & messaging, plus the adapter's privacy calls) and a Data safety and privacy policy update before the build ships.
5. Friendly clicks must not get the AdMob account limited for invalid traffic. During the closed test that means: the founder's phones are AdMob test devices; **Unity test mode is on** (Unity dashboard → Monetization → Testing, project-wide) because AdMob test devices don't cover mediated Unity demand; and testers get a written "please don't tap ads" note. Unity test mode is switched off at the production launch (Google's guide: disable test mode for AdMob and Unity before release).
6. More content is a separate, non-code track: publish remote pictures weekly through the existing #43 pipeline.
7. Real ad earnings start at the **production** launch, not in closed test. AdMob only links Android apps that are publicly available on Play; an unlinked app gets limited ad serving, and the app readiness review starts only after linking ([AdMob 10564477](https://support.google.com/admob/answer/10564477), [AdMob 9989980](https://support.google.com/admob/answer/9989980)). So the closed-test build proves the wiring; linking, app-ads.txt verification and the readiness review are production-launch steps.

## Landscape (searched 2026-10-18)
- AdMob's Unity Ads adapter supports bidding and waterfall for interstitial and rewarded; bidding needs adapter 4.16.0.1+. Setup: Unity dashboard placements set to Bidding, then add Unity Ads as a bidding ad source on each AdMob ad unit, then add Unity Ads to the GDPR and US-states ad partner lists, then set the Unity SDK privacy settings in the app. Load calls need an Activity context. ([Google guide](https://developers.google.com/admob/android/mediation/unity?hl=en))
- New or unverified apps get limited ad serving until app-ads.txt is verified and the app readiness review (2-3 days) completes; crawling takes up to 24 h; the file must sit at the root of the developer website on the Play listing. ([AdMob 10564477](https://support.google.com/admob/answer/10564477), [AdMob 15948559](https://support.google.com/admob/answer/15948559))
- Unity Ads is not a registered TCF vendor: it doesn't read the TC string, so consent must be passed via the mediator/adapter, and Unity must be enabled as a custom ad partner in Privacy & messaging. ([Unity docs](https://docs.unity.com/en-us/ads-android/4.20.0/privacy/developer-consent/frameworks/gdpr/google-consent-framework-support))
- **Insight:** most games add networks to raise eCPM on lots of impressions. Gemmory deliberately serves few (an estimate of about 1-3 per player per day from the caps, pending the Firebase numbers), so real AdMob demand plus verified app-ads.txt is most of the value; Unity bidding is a modest add-on on a small base.

## Approaches Considered

- **B: One issue, AdMob live + Unity bidding (chosen).**

## Recommended Approach: B
One issue (T34) covering, in order:

1. **Accounts and console (founder, non-code)**
   - AdMob: create the production app, one rewarded unit and one interstitial unit. Set up payments.
   - Unity: create the project and two bidding placements (rewarded, interstitial); note the Game ID and Placement IDs.
   - AdMob mediation: add Unity Ads as a **bidding** source on both units (accept the bidding partnership).
   - Privacy & messaging: GDPR message already exists (UMP); enable Unity Ads under Custom ad partners. Create and publish a US-states message (if none exists yet) with Unity Ads in its ad partners, because the `privacy.consent` logic in step 3 reads the opt-out that message records.
2. **app-ads.txt**
   - Create a GitHub Pages user/org site (`BrewingBytes/brewingbytes.github.io`) with `app-ads.txt` at its root: the AdMob line from the console plus Unity's lines.
   - Set it as the developer website in Play Console. Optionally move the privacy policy there too (keep the current URL working until a release updates `PRIVACY_POLICY_URL`).
   - Publish the file now. Verifying the app in AdMob is a **production-launch** checklist item, because AdMob can only crawl it once the app is linked to the public listing (premise 7).
3. **App code**
   - **ID source:** the production IDs are not secret, so they are committed in `gradle.properties` as `gemmory.admob.appId`, `gemmory.admob.rewardedUnit` and `gemmory.admob.interstitialUnit` (release AABs are built locally with `:androidApp:bundleRelease`, README → Release, and any future CI reads the same committed file). The release build type reads them: `gemmory.admob.appId` goes into the manifest's `com.google.android.gms.ads.APPLICATION_ID` through `manifestPlaceholders` per build type, and the two unit IDs go through `buildConfigField`. Debug and connected tests keep Google's test IDs. Remove the hardcoded constants in `AdMobGateway.kt`.
   - **Fail closed:** a `validateReleaseAdIds` task that `bundleRelease` and `assembleRelease` depend on (debug tasks and connected tests don't run it) fails if any of the three is missing, blank, or uses the test publisher `ca-app-pub-3940256099942544`. The rule is a plain Kotlin function in the build logic, called by the task and unit-tested directly. A release can never ship with test ads or no ads.
   - Add the Unity Ads SDK and Google's Unity adapter to `gradle/libs.versions.toml`: `com.unity3d.ads:unity-ads` and `com.google.ads.mediation:unity`, adapter ≥ 4.19.0.1 (current 4.21.0.0 on 2026-10-18).
   - **GDPR consent to Unity:** no hand-written mapping. Adapter 4.19.0.1+ automatically forwards the GDPR consent UMP stores in `IABTCF_AddtlConsent` to the Unity SDK when GDPR applies ([Google guide](https://developers.google.com/admob/android/mediation/unity?hl=en), changelog). Unity is a custom ad partner in the UMP message (step 1), so its yes/no is in that string; granted, denied and withdrawn (privacy options form) all flow through it on the next request with no app code. The app must not also write `gdpr.consent` metadata, so the two can't disagree.
   - **US-states consent to Unity:** `privacy.consent` metadata, written by `ConsentManager` on every launch after `requestConsentInfoUpdate` completes and again when the privacy options form closes (`onLaunch`, `showPrivacyOptions`). Value, from the GPP data UMP stores in default SharedPreferences:
     - **Source:** `IABGPP_HDR_GppString` (the full GPP string), decoded with IAB Tech Lab's Java GPP library (`iabgpp-java`, artifact `com.iabgpp:iabgpp-encoder`; confirm the coordinates at build time). No hand-written bit parsing.
     - **Sections checked:** every US section present: `usnat` (section id 7) and any US state section (ids 8-12 and later state ids the library knows).
     - **Opt-out rule:** `false` if any checked section has `SaleOptOut == 1`, `SharingOptOut == 1` or `TargetedAdvertisingOptOut == 1` (state sections without a `SharingOptOut` field are covered by the other two; 1 = opted out; 0 = not applicable and 2 = did not opt out both count as no opt-out).
     - **No GPP string, or no US section in it** (users outside US states): `true`.
     - **String present with a US section, but it fails to decode:** `false` (fail safe), and a non-fatal goes to Crashlytics.
     - **Tests** use strings captured from UMP on a debug build with `DebugGeography.REGULATED_US_STATE`: one opted out of sale, one opted out of sharing, one not opted out, plus a no-GPP case and a malformed case.
   - **Ordering:** the Unity metadata write happens before `MobileAds.initialize` (`AdMobGateway.start()`, `ads/AdMobGateway.kt:105-125`), which already waits for `canRequestAds`. `start()` awaits the first write; a test fakes the metadata sink and asserts the write precedes initialize.
   - **Activity context:** Google's guide wants an Activity context for interstitial loads. Today `AdMobGateway` loads with the application context (`ads/AdMobGateway.kt:82,133`) and preloads ahead of time. Keep rewarded on the application context. For interstitials, load from the current resumed Activity, held as a `WeakReference` that's cleared in `onDestroy`, so no Activity outlives its screen. If none is resumed, skip the preload and retry on the next resume. Check with LeakCanary or a heap dump on a debug build.
   - Test devices: the founder's phones registered in the AdMob console (so release builds on them get test ads), plus Unity test mode on in the dashboard for the whole closed test (premise 5).
   - No change to `AdPolicy`, `RewardedRules`, the daily ledger or any surface where ads appear.
4. **Compliance**
   - Re-do `docs/play-compliance.md` Data safety for Unity Ads (read Unity's Play data disclosure), update `docs/privacy-policy.md` "Who receives data" with Unity, merge before the build ships.
   - **Play Console:** update and submit the Data safety form to match, and confirm the hosted privacy policy URL shows the Unity change, before the build is promoted to closed.
   - Check the merged manifest for new permissions Unity adds.
5. **Verification**
   - Unit tests: release config resolves to the committed IDs, debug to test IDs; release configuration fails on missing, blank or test-publisher IDs; `privacy.consent` is `false` after a US-states opt-out, `true` with no opt-out, rewritten after the privacy options form closes (withdrawal case); decoding cases from captured UMP strings: sale opt-out → `false`, sharing opt-out → `false`, targeted-advertising opt-out → `false`, no opt-out → `true`, no GPP string or no US section → `true`, malformed → `false` plus a non-fatal; the Unity write precedes `MobileAds.initialize`; `validateReleaseAdIds` accepts real IDs and rejects missing, blank and test-publisher IDs.
   - AdMob Ad Inspector on a test device: confirm Unity Ads appears as a bidding source and both formats fill.
   - Existing ad-policy tests stay green (caps, no canvas ads).
6. **Rollback**
   - Unity can be switched off with no release: disable it as a bidding source on both AdMob units, and AdMob demand alone keeps serving.
   - Trigger: a Crashlytics crash or ANR cluster with Unity SDK frames, or a Play vitals crash/ANR regression after the release. The SDK removal then ships in the next version.

### R3-1 — completeness (minor)

**Problem**

> The opt-out rule checks only SaleOptOut and SharingOptOut. State sections such as usva, usco, usut and usct have no SharingOptOut field; their ad-relevant opt-out is TargetedAdvertisingOptOut, which usnat also carries. If UMP ever recorded a targeted-advertising opt-out without also setting SaleOptOut, the user would get privacy.consent = true. UMP's single 'do not sell or share' choice probably sets all of these fields together, so in practice the rule likely gives the right answer. The design doesn't say this.

**Remedy**

> Either add TargetedAdvertisingOptOut == 1 to the opt-out rule, or state that UMP's US-states opt-out sets SaleOptOut in every section it writes and that the captured test strings confirm it.
